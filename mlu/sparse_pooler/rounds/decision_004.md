## Pitfalls and Anti-pattern Consultation

- Consulted `references/anti-patterns.md`. No entry matches this intervention. The recorded failures concern winner-tree expert selection, sort networks, dynamic `tl.gather` compaction, and cumsum compaction in grouped top-k — none apply to a host-side launcher replacement and output buffer cache. The cache-key, invalidation, lifetime, and concurrency semantics are explicit in the Host Plan, addressing the buffer-reuse pitfalls flagged in the triton_mlu target profile.

- Consulted `references/bottleneck-judgment.md`. The accepted reference device_ratio is 0.346 (mixed). Wall time is 606.76 us/call and device time is 210.12 us/call, so roughly 396 us/call (~65% of wall) is host-side. The host-side Python loop and D2H sync were already eliminated in Round 001; the remaining host time is launcher, wrapper, allocation, and harness-fixed cost. This round targets the launcher and allocation components, which are classified as Potentially Compressible per the bottleneck-judgment table. The device-side kernels are unchanged and outside the change boundary. The compressible-versus-fixed host time table records that the harness device synchronization and seed setup are Fixed for the regime; this round does not claim to reduce those.

- Consulted `prompts/coder_targets/triton_mlu.md`. `fast_libentry` is explicitly listed as an importable form (`from triton.runtime import fast_libentry`) with the observed compatible pattern initializing `fast_libentry()(_kernel)` from a retained class body when the loader requires it. The evidence is `flexattention/triton_flexattention_003.py`, which uses exactly this pattern (class-body `globals()["_sdpa_v3_fast"] = fast_libentry()(_sdpa_v3_kernel)`) and passed the harness AST loader. The `flexattention/log.md` Entry 003 records that `fast_libentry()` reduces the per-launch host overhead substantially (recorded as ~60 us -> ~10 us in the fused_moe v3 experience). Output caching and removal of a redundant device context are flagged as Host Plan patterns that require explicit ownership, cache-key, invalidation, concurrency, device, and stream semantics — all of which are specified in the Host Plan above. This round does NOT remove a `torch.mlu.device()` context (the accepted reference has none), so that pitfall is not applicable.

- Consulted the accepted reference `triton_sparse_pooler_001.py`. The forward path is: (1) `self.decoder(self.layer_norm(self.act(self.dense(hidden_states))))` — 4 library ops; (2) `torch.empty((num_seq, vocab_size), dtype=torch.float32, device=device)` — one allocation per forward; (3) `_sparse_pooler_max_kernel[grid](...)` — one Triton launch with grid (4, 30) = 120 programs via the default launcher. This round replaces step 2 with a cache check (steady-state hit reuses the buffer) and step 3's launcher with `fast_libentry()`. Steps 1 and 3's kernel body are unchanged.

- The harness AST loader (`auto_bench._filter_module_ast`) strips module-level non-literal assignments. A module-level `_fast = fast_libentry()(_sparse_pooler_max_kernel)` would be stripped, causing a `NameError` at runtime. The proven workaround (from `flexattention/triton_flexattention_003.py`) is to populate the wrapped kernel from inside the `ModelNew` class body via `globals()["_sparse_pooler_max_fast"] = fast_libentry()(_sparse_pooler_max_kernel)`. ClassDef nodes are retained by the loader, so the class body executes at import time and injects the wrapped kernel into module globals. Coder MUST use this exact pattern. The triton_mlu target profile records both `from triton.runtime import fast_libentry` and `from triton.runtime.fast_libentry import fast_libentry` as observed forms; Coder should use the form that compiles on this runtime, with `from triton.runtime import fast_libentry` as the first choice (matches the flexattention v3 evidence).

- The cached output buffer is per-instance (`self._out_cache`). The harness runs `model_new.load_state_dict(model.state_dict())` before timing; this updates `self.decoder.weight` etc. but does NOT touch `self._out_cache` (the cache is initialized to None in `__init__` and is not a registered parameter or buffer). The first timed forward allocates the buffer; subsequent timed forwards reuse it because the cache key (num_seq=4, vocab_size=30522, dtype=fp32, device=mlu:0) is constant across the warmup and repeat loop. This is the intended steady-state behavior.

- Returning `[out[i] for i in range(num_seq)]` from a cached `out` tensor: the returned list of slices shares storage with the cached buffer. The harness reads these slices for correctness comparison and does not write to them. The next forward overwrites the cached buffer in place before any consumer of the previous slices is expected to read them (the harness consumes each forward's output before the next forward). This matches the flexattention v3 pattern, which returns `out.reshape(T, H * D)` from a cached buffer. If the harness were to retain references to previous outputs and compare them after a subsequent forward, the in-place overwrite would be a correctness hazard; the harness does not do this (it compares v0 vs v1 per forward and does not retain cross-forward references), so the pattern is safe here. Coder must NOT introduce any cross-forward aliasing beyond what the accepted reference already does (the accepted reference returns slices of a per-forward `torch.empty`, which is also not retained across forwards).

- The `_out_cache` is a plain Python attribute, not an `nn.Module` buffer or parameter. It will not be picked up by `state_dict()` or `load_state_dict()`, so load_state_dict compatibility is preserved. Coder must NOT register it via `self.register_buffer` or `self.register_parameter` — that would change the state_dict shape and break load_state_dict.

- `num_warps=1` is the proven launch configuration and is preserved unchanged. `num_warps=2` must not be used. The fast_libentry wrapper changes the launcher path, not the kernel's num_warps; the num_warps=1 argument is passed through to the wrapped kernel exactly as in the accepted reference.

- Per `references/invariants.md`, buffer allocation, reuse, cache keys, invalidation, ownership, and lifetime follow the validated Host Plan. The cache key includes shape (num_seq, vocab_size), dtype, and device — all mandatory compatibility components. State owned by one ModelNew instance is not shared across instances or concurrent forwards. The caller-selected device and current stream are preserved (no device context introduced). This round satisfies all buffer/device/stream lifecycle invariants.

- Round 002 evidence shows `BLOCK_V=1024` is the best-known tiling for the fused kernel on this runtime; this round keeps BLOCK_V=1024 unchanged. Round 003 evidence shows `tl.dot` with small M is inefficient on MLU590-H8; this round does not use `tl.dot` and does not modify the kernel body. No device-side primitive is changed.

- The fused kernel grid is (4, 30) = 120 programs. The default Triton launcher issues a host-side setup for each program. `fast_libentry` is expected to reduce this per-launch host overhead. The flexattention v3 evidence (similar small-shape regime, single-kernel launch) recorded a host overhead reduction of ~70 us/call when combining fast_libentry + cached buffer + removing device context. This round uses fast_libentry + cached buffer but does NOT remove a device context (the accepted reference has none), so the expected host savings are bounded above by the flexattention v3 figure and conservatively estimated at 30-40 us/call for this project (the accepted reference's fused kernel is a different kernel with a different grid).

- The expected wall improvement of 6.0% is justified as follows: the accepted wall time is 606.76 us/call. A 5% improvement requires 30.34 us/call of wall savings. The host-side overhead is ~396 us/call, of which the launcher and allocation components are the target. The flexattention v3 evidence shows the launcher + allocation components can be reduced by tens of microseconds in a similar small-shape regime. A conservative 30 us/call savings (5% of 606.76) is the floor; the 6.0% expectation (~36 us/call) is slightly above the floor and well below the flexattention v3 upper bound (~70 us/call). If fast_libentry alone delivers ~20 us/call and the cached buffer delivers ~10-15 us/call, the combined ~30-35 us/call meets the 5% threshold.

- The primary risk is that the host-side launcher overhead for the (4, 30)=120-program grid may already be small enough that fast_libentry's savings are below 5% wall, or that the per-forward `torch.empty` allocation is already cheap on this runtime. This risk is accepted because the intervention is falsifiable: the mechanism observables (`output_allocations_per_call`, `fused_kernel_us_per_call`, `device_us_per_call`, `kernel_count_per_call`) will directly reveal whether the host-side change produced wall savings without changing device time. If the wall improvement is below 5%, the hypothesis is falsified and the round terminates as no-improvement; the device-side guardrails (`device_us_per_call` must not increase, `kernel_count_per_call` remains 5) ensure the change does not regress device behavior.

## Rationale and Evidence

The accepted Round 001 report (`rounds/report_001.md`) records:

- Benchmark wall time median: 0.606758 ms (606.76 us/call), a 33.39% improvement over the baseline.
- Device time: 210.12 us/call; device_ratio: 0.346 (mixed).
- Kernel count: 5 per call (down from 10).
- The fused `_sparse_pooler_max_kernel` is the dominant device kernel at 98.73 us/call (47.0% of device time).
- The decoder matmul (`MLUFusedMatMulGepm`) is the second-largest device kernel at 90.36 us/call (43.0%).
- The remaining host time (~396 us/call, ~65% of wall) is launcher, wrapper, allocation, and harness-fixed cost. The Python loop and D2H sync were eliminated in Round 001.

The rejected Round 002 report (`rounds/report_002.md`) records:

- BLOCK_V 1024->2048 was falsified: the fused kernel got slower (99.71 -> 102.42 us/call).
- The `kernel-tile-tuning` change family is exhausted for this kernel on this runtime.
- The candidate device ratio is 0.343 (mixed). Wall time 621.85 us/call, device 213.02 us/call, so roughly 409 us/call (~66%) is host-side.

The rejected Round 003 report (`rounds/report_003.md`) records:

- The decoder matmul fusion via `tl.dot` with small M was falsified: the new fused kernel at 373.31 us/call is 184.22 us/call SLOWER than the 191.44 us/call combined cost of the two kernels it replaced.
- The `kernel-matmul-fusion` change family via `tl.dot` with small M is exhausted on this runtime.
- The candidate device ratio is 0.461 (diagnostic, mixed). Wall time ~853 us/call (screening mean), device 392.94 us/call, so roughly 460 us/call (~54%) is host-side.
- The accepted reference device profile is unchanged: fused kernel ~99.52, decoder matmul ~91.92, dense matmul ~8.83, LayerNorm ~7.48, GELU ~4.57 us/call.

The intervention targets the host-side launcher and allocation overhead, which is ~396 us/call (~65% of the accepted wall time) and is the largest single component of wall time. The device-side kernels (210.12 us/call total) are unchanged — Rounds 002 and 003 have exhausted the most obvious device-side tuning and fusion opportunities on this runtime, and a third device-side attempt would risk the third miss that trips the `valid_no_improvement_limit=3` stop criterion. The host side is a separately observable mechanism that has not yet been attacked directly.

The `change_family` is `host-allocation-reuse`, which is different from the last three rounds (Round 001: `kernel-fusion`, Round 002: `kernel-tile-tuning`, Round 003: `kernel-matmul-fusion`). This is required by the v2 Designer contract after a `no-improvement` result.

The expected wall improvement of 6.0% is justified by the following evidence:

1. The accepted wall time is 606.76 us/call. A 5% improvement requires 30.34 us/call of wall savings. The host-side overhead is ~396 us/call, of which the launcher and allocation components are the target. The launcher component is compressible (per `bottleneck-judgment.md`), and the allocation component is compressible (per `bottleneck-judgment.md`).

2. The flexattention v3 evidence (`flexattention/triton_flexattention_003.py`, `flexattention/log.md` Entry 003) records that combining `fast_libentry` + cached output buffer + removing device context reduced host overhead from ~159 us/call to ~89 us/call (~70 us/call savings) in a similar small-shape regime (T=83, single-kernel launch). The `fast_libentry` component alone was recorded as reducing the per-launch host overhead from ~60 us to ~10 us in the fused_moe v3 experience (`flexattention/log.md` Entry 003). This round uses `fast_libentry` + cached buffer but does NOT remove a device context (the accepted reference has none), so the upper bound on host savings is the flexattention v3 figure (~70 us/call).

3. A conservative estimate for this project: `fast_libentry` saves ~20 us/call of launcher overhead for the (4, 30)=120-program grid (smaller than the flexattention grid but with the same launcher path), and the cached output buffer saves ~10-15 us/call of `torch.empty` allocation overhead. Combined: ~30-35 us/call, which is 5.0-5.8% of 606.76 us/call. The 6.0% expectation (~36 us/call) is slightly above this conservative floor and well below the flexattention v3 upper bound (~70 us/call).

4. The device-side guardrails ensure the change does not regress device behavior: `fused_kernel_us_per_call` must remain ~98.73 us/call, `device_us_per_call` must remain ~210.12 us/call, and `kernel_count_per_call` must remain 5. If any of these move, the change has inadvertently affected the device side and the hypothesis is falsified regardless of the wall result.

The primary risk is that the host-side launcher overhead for the (4, 30)=120-program grid may already be small enough that `fast_libentry`'s savings are below 5% wall, or that the per-forward `torch.empty` allocation is already cheap on this runtime. This risk is accepted because:
- The intervention is falsifiable via the four mechanism observables.
- The change_family is new (host-allocation-reuse), so a no-improvement result would not be a third repetition of an exhausted family.
- The device-side guardrails ensure the change cannot regress device time, so the downside risk is bounded to "no improvement" rather than "regression."

Rejected alternatives for this round:

- (A) `kernel-elementwise-fusion`: fuse dense matmul + GELU + LayerNorm into one Triton kernel. The three kernels cost 8.42 + 7.21 + 5.40 = 21.03 us/call (3.5% of wall). Even fully eliminating them would not clear the 5% threshold, and the fusion would require a larger change boundary (the full MLM head) for limited device savings. The `kernel-elementwise-fusion` change family is also closer to the exhausted `kernel-fusion` family than `host-allocation-reuse` is.

- (B) `library-op-substitution`: replace one of the library ops (e.g., GELU or LayerNorm) with a faster equivalent. The individual kernels are too small (5-8 us/call each) to yield 5% wall, and PyTorch's MLU library ops are already tuned for this architecture.

- (C) `kernel-reduction-strategy`: change the reduction strategy of the existing fused kernel (e.g., load each logits row once and accumulate across vocab tiles). Round 002 evidence shows the bottleneck in the fused kernel is per-program elementwise compute, not launch-dispatch overhead or reduction strategy. This family is close to the exhausted `kernel-tile-tuning` family.

- (D) `host-dispatch-reduction`: reduce PyTorch op dispatch overhead by fusing the four library MLM head ops into fewer dispatches. This overlaps with (A) and requires a kernel-side change, moving the change_family toward `kernel-fusion` rather than a pure host change. The host-allocation-reuse intervention is a cleaner pure-host change that targets the same host overhead without touching device kernels.

Noncanonical history: the Round 002 BLOCK_V=2048 tuning (`triton_sparse_pooler_002.py`) and the Round 003 decoder matmul fusion (`triton_sparse_pooler_003.py`) are rejected candidates and never starting points. The Round 001 fused kernel (`triton_sparse_pooler_001.py`) remains the canonical starting point. Round 002 evidence (BLOCK_V=1024 is best-known, kernel-tile-tuning exhausted) and Round 003 evidence (tl.dot with small M inefficient on MLU590-H8, kernel-matmul-fusion exhausted) are noncanonical for future rounds but inform the choice of change_family: the device-side kernel-tuning and kernel-matmul-fusion families are exhausted, so the next round must target a different mechanism. The host-side launcher and allocation overhead is the largest unattacked component of wall time and is the chosen target.
